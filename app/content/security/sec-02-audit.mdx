<GoalLine>

Audit the cloned raffle project end to end: scope it, read its call graph, file one finding
with a failing test as the proof, and write the report as a Foundry test.

</GoalLine>

<DoIt note="Your OS commands. Expected outputs are under each step.">

This is the exact workflow a first audit engagement uses:

```bash
git clone https://github.com/Cyfrin/4-puppy-raffle-audit
cd 4-puppy-raffle-audit
make
forge test --match-path test/PuppyRaffle.t.sol
```

Then read the scope file `README.md` for the parts the engagement bounds you to:

```bash
git log --oneline -5
cat README.md
```

Your first job is not the exploit: it is the scope paper. Write it as a short
Markdown file, `SCOPE.md`, with the commit hash, the files in scope, the chain to
use, and the roles.

<Expected>
Commit: 2a47715b30cf11ca82db148704e67652ad679cd8
In scope: ./src/PuppyRaffle.sol
Solc: 0.7.6
Chain: Ethereum
Roles: Owner (fee address), Player (entrants)
</Expected>

Keep that file. Auditors write it before touching the code.

</DoIt>

<SpotIt>

Route the call graph by hand before you write a single line of attack code:

```bash
grep -rn "function " src/PuppyRaffle.sol
```

Draw the edges on paper: who calls what, what reads what, what can anyone call?
Rank the entry points. This recon is what separates an audit from a hack.

</SpotIt>

<FixIt>

Turn your scope paper into the first real artifact: a finding in Foundry test form.
Write the failing test first, run it to see it fail, then fix the contract and watch it
go green. The report stays in Markdown; the proof lives in the test.

</FixIt>

## The report is the deliverable

A finding is a compact document with five fields:

- **Severity** — critical, high, medium, low
- **Impact** — what does the attacker actually get (tokens, ETH, governance control)
- **Likelihood** — how easy is this to trigger, and how many paths lead here
- **Proof of concept** — a Foundry test that fails now and passes after the fix
- **Recommended fix** — the exact change to make

The report is what gets you paid. Write it before you ever run again, and keep the
test beside it.
