## Two ways arithmetic kills a contract

On pre-0.8 compilers, `a * b` that exceeds uint256 wraps silently to a small
number. The 2018 BEC incident used exactly this: a `batchTransfer` computed
`uint256 amount = cnt * _value;` before checking balances, so a crafted
`_value` made `amount` wrap to near zero, passed the require, and credited
receivers with enormous balances. Exchanges kept trading until the market
caught on.

Since 0.8, overflow reverts instead of wrapping. That closes the wrap, but it
opens the other side: arithmetic you expected to be large now reverts, and
if the only path to someone's funds runs through that arithmetic, their funds
are bricked. DoS by math.

<DoIt note="Reproduce both failure modes locally.">

```bash
mkdir ccc-lab && cd ccc-lab

```

Write two contracts in `src/`: one pinned to `pragma solidity 0.7.6;` with a
`batchTransfer`-shaped multiplication, and one 0.8.x contract with an
unbounded payout loop. Tests:

```bash
forge test --match-test testOverflow -vvv
forge test --match-test testBrickTheLoop -vvv
```

<Expected>
[FAIL] testOverflow: multiplication wrapped (0.7.6, pre-checked math)
[PASS] testBrickTheLoop: loop gas grew past the block limit with 2000 entries
</Expected>

The first test proves value from nothing. The second proves the payout can
never complete again.

</DoIt>

<SpotIt>

```bash
grep -rn "for (uint\|while (\|\.length" src/
grep -rn "pragma solidity" src/
grep -rn "address(this).balance\|\.transfer(\|\.call{" src/
```

Rank every hit: does iteration count depend on user-supplied or ever-growing
state? Does any payout loop share one transaction with all recipients? Is any
arithmetic on a 0.7-era compiler doing security-critical multiplication? The
loop hits rank higher than the wraps on modern compilers.

</SpotIt>

<FixIt>

```solidity
// 1. Pull payments: each user claims, one at a time
function claim() external {
    uint256 amount = s_owed[msg.sender];
    require(amount > 0, "nothing owed");
    s_owed[msg.sender] = 0;
    (bool ok, ) = msg.sender.call{value: amount}("");
    require(ok);
}

// 2. Bounded iteration when you must loop
uint256 constant MAX = 100;
for (uint256 i = 0; i < n && i < MAX; i++) { ... }
```

Compile on 0.8.x for checked math, then re-run both tests: the wrap test
reverts on arithmetic, and the loop test can no longer be bricked past MAX.

</FixIt>

## Real-world case: BEC batchOverflow, April 2018

The BEC token's `batchTransfer` on a pre-0.8 compiler multiplied receiver
count by value with no overflow guard. Two attacker transactions minted
roughly 70 trillion BEC from thin air (and similarly hit SMT and other tokens
the same week). The SWC-101 registry carries the actual vulnerable
`BecToken` source as its reference sample.

The vulnerable code, officially catalogued: https://swcregistry.io/docs/SWC-101

Sigma Prime's writeup of the same era's arithmetic disasters: https://blog.sigmaprime.io/solidity-security.html
